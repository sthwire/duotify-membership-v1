# 功能規範: 會員註冊流程

**功能分支**: `001-member-registration`
**建立**: 2025-10-18
**狀態**: 澄清完成，準備規劃
**輸入**: 使用者描述: "# 會員註冊流程

我們的核心目標是讓新使用者能透過一個簡單、安全的流程，順利註冊帳號並完成 E-Mail 驗證，以便使用平台功能。

整個註冊是一個單向流程，無法返回上一步。使用者首先需要填寫身分證字號、姓名等資料，並設定一組 8 到 20 碼、包含英文大小寫與數字的密碼。系統會檢查身分證字號，防止重複註冊。

送出資料後，系統會寄出一封內含 6 位數驗證碼的 E-Mail，有效時間為 5 分鐘。使用者必須手動輸入驗證碼來完成驗證。

如果使用者未完成 E-Mail 驗證，依然可以用剛設定的帳號密碼登入，但部分功能將受限。直到輸入正確的驗證碼後，帳號所有功能才會被啟用。註冊完成後，系統不會自動登入。

為了讓流程單純，我們不做社群帳號註冊、不提供密碼強度提示，也不支援點擊 E-Mail 連結直接驗證。"
**語言**: 繁體中文 (zh-TW)

## 用戶場景與測試 *(強制)*

### 用戶故事 1 - 完成基本註冊 (優先級: P1)

新使用者能夠透過簡單的表單填寫個人資料並設定密碼，成功建立帳號。

**為什麼這個優先級**: 這是註冊流程的核心功能，所有其他功能都依賴於成功建立帳號。

**獨立測試**: 可以通過檢查資料庫中是否建立新用戶記錄，並驗證用戶能以設定密碼登入來完全測試。

**接納情景**:

1. **給定** 用戶在註冊頁面, **當** 用戶填寫有效的身分證字號、姓名和符合規定的密碼, **然後** 系統建立新帳號並顯示註冊成功訊息
2. **給定** 用戶嘗試使用已存在的身分證字號註冊, **當** 用戶提交表單, **然後** 系統顯示錯誤訊息並阻止重複註冊
3. **給定** 用戶輸入不符合密碼規定的密碼, **當** 用戶提交表單, **然後** 系統顯示密碼格式錯誤訊息並要求重新輸入

---

### 用戶故事 2 - 完成 E-Mail 驗證 (優先級: P1)

註冊後的用戶能夠接收驗證郵件並輸入驗證碼來啟用完整帳號功能。

**為什麼這個優先級**: E-Mail 驗證是確保帳號安全性和完整功能啟用的關鍵步驟。

**獨立測試**: 可以通過檢查驗證郵件是否寄出、驗證碼是否正確驗證帳號狀態來完全測試。

**接納情景**:

1. **給定** 用戶成功註冊帳號, **當** 系統發送驗證郵件, **然後** 用戶在 5 分鐘內收到包含 6 位數驗證碼的郵件
2. **給定** 用戶收到驗證郵件, **當** 用戶輸入正確的 6 位數驗證碼, **然後** 帳號狀態變為已驗證並啟用所有功能
3. **給定** 用戶輸入錯誤的驗證碼, **當** 用戶提交驗證, **然後** 系統顯示錯誤訊息並允許重新輸入
4. **給定** 驗證碼已過期 (超過 5 分鐘), **當** 用戶嘗試使用過期驗證碼, **然後** 系統顯示驗證碼過期訊息並提供重新發送選項

---

### 用戶故事 3 - 使用未驗證帳號登入 (優先級: P2)

未完成 E-Mail 驗證的用戶仍能登入但功能受限。

**為什麼這個優先級**: 提供基本可用性同時鼓勵用戶完成驗證。

**獨立測試**: 可以通過未驗證用戶登入後檢查功能可用性來完全測試。

**接納情景**:

1. **給定** 用戶帳號未驗證, **當** 用戶使用正確帳密登入, **然後** 系統允許登入但顯示功能受限提示
2. **給定** 未驗證用戶嘗試存取受限功能, **當** 用戶點擊受限功能, **然後** 系統顯示需要驗證郵件的提示並提供驗證選項

### 邊緣案例

- 網路連線中斷導致註冊表單提交失敗
- 用戶在驗證碼過期前嘗試多次輸入錯誤驗證碼
- 郵件系統故障導致驗證郵件無法送達
- 用戶嘗試使用無效或格式錯誤的身分證字號

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須允許用戶填寫身分證字號、姓名和密碼來建立新帳號
- **FR-002**: 系統必須驗證身分證字號格式並檢查是否重複註冊
- **FR-003**: 系統必須驗證密碼符合 8-20 字元且包含大小寫英文與數字的要求
- **FR-004**: 系統必須在註冊成功後發送包含 6 位數驗證碼的 E-Mail
- **FR-005**: 系統必須允許用戶手動輸入驗證碼來完成帳號驗證
- **FR-006**: 系統必須在驗證碼有效期 (5 分鐘) 內接受驗證
- **FR-007**: 系統必須允許未驗證用戶登入但限制部分功能
- **FR-008**: 系統必須在驗證完成後啟用帳號所有功能
- **FR-009**: 系統必須在註冊完成後不自動登入用戶
- **FR-010**: 系統必須支援雙重角色系統：一般用戶與管理員
- **FR-011**: 新註冊用戶預設為一般用戶角色
- **FR-012**: 管理員角色必須由開發團隊手動指定

### User Experience & Consistency Requirements

Per the project constitution (Principle III), this feature MUST include:

- **UX-001**: 所有 UI 元件必須遵循既定的設計系統模式
- **UX-002**: 錯誤訊息必須清晰、可行動且用戶友善
- **UX-003**: 載入狀態與用戶回饋必須可見且提示性
- **UX-004**: 功能必須符合 WCAG 2.1 AA 可訪問性標準最低要求
- **UX-005**: API 回應必須使用一致的數據格式與錯誤結構
- **UX-006**: 用戶工作流程必須符合既有互動模式
- **UX-007**: 本地化/多國語言支援必須在設計中考量

### Performance Requirements

Per the project constitution (Principle IV), this feature MUST include:

- **PERF-001**: API 回應時間必須 ≤ 500ms (p95 正常負載下)
- **PERF-002**: UI 互動必須在 ≤ 100ms 內回應才能感覺即時
- **PERF-003**: 資料庫查詢必須使用適當索引最佳化
- **PERF-004**: 負載測試必須在發布前執行

### Security & Privacy Requirements

- **SEC-001**: 系統必須使用基於 Session 的認證搭配安全的 HTTP-only cookies
- **SEC-002**: 用戶密碼必須使用強加密演算法雜湊儲存
- **SEC-003**: 驗證碼必須在單次使用後失效，防止重複使用
- **SEC-004**: 敏感用戶資料（如身分證字號）必須加密儲存
- **SEC-005**: 系統必須實作基於 IP 的速率限制，每個 IP 每小時最多允許 5 次註冊嘗試
- **SEC-006**: 超過速率限制時系統必須顯示清晰的錯誤訊息並建議稍後重試

### Integration & External Dependencies

- **INT-001**: 系統必須使用第三方郵件服務 API（如 SendGrid、Mailgun）發送驗證郵件
- **INT-002**: 郵件服務必須支援 HTML 格式郵件與自訂寄件者
- **INT-003**: 系統必須處理郵件發送失敗的情況並記錄錯誤
- **INT-004**: 郵件服務 API 必須支援重試機制以處理臨時故障

### Key Entities *(include if feature involves data)*

- **用戶帳號**: 代表註冊用戶，包含身分證字號、姓名、E-Mail、密碼雜湊、驗證狀態、建立時間、Session ID
- **驗證記錄**: 追蹤發送的驗證碼，包含驗證碼、發送時間、過期時間、使用狀態

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用戶必須能在 3 分鐘內完成整個註冊與驗證流程
- **SC-002**: 90% 的用戶必須能在首次嘗試中成功完成註冊
- **SC-003**: 驗證郵件必須在註冊後 30 秒內送達
- **SC-004**: 系統必須支援每分鐘 10 個並發註冊請求而不降級
